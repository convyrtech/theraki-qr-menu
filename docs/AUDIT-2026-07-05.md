# Аудит The Raki — итоговый отчёт (после адверсариальной проверки)

## 1. Вердикт

**Показ меню (витрина) — почти готов, но с двумя тихими отказами; подсистема заказов/счетов через публичный `/api/order` — НЕ готова к проду: есть удалённо-эксплуатируемые блокеры (флуд + порча счёта без авторизации).** 31 подтверждённая находка, критичных крашей «для всех прямо сейчас» нет, но 4 находки при живом ресторане ведут себя как High, а не Medium.

Оговорка по методу: весь аудит — статический разбор кода. Ни один сценарий не воспроизведён в браузере / реальном боте / под нагрузкой (см. §5). Метки тяжести ниже — моя пере-оценка под бизнес-контекст (живое заведение, платящие гости, 2 админа владелец+жена), а не исходные метки аудитора (там всё было medium/low).

## 2. Находки по тяжести

### HIGH — удалённо-эксплуатируемо / ломает ядро бизнеса

**H1. Публичный `/api/order` без авторизации: лимит обходится параллельным всплеском → флуд чата смены → бан бота в Telegram → реальные заказы не доходят на кухню**
`src/lib/orders.ts:26`, `src/app/api/order/route.ts:38` *(объединяет находки 10+12)*
- Простыми словами: любой человек из интернета, зная адрес, шлёт 200 запросов за секунду. Проверка лимита читает счётчик ДО отправки, а счётчик пишется ПОСЛЕ отправки — поэтому все 200 проходят и все летят тикетами персоналу. Бот упирается в лимит Telegram (429), после чего настоящие заказы гостей возвращают ошибку 502 «позовите официанта».
- Фикс: атомарный счётчик-окно одним SQL (`INSERT … ON CONFLICT DO UPDATE … RETURNING cnt`) и вызывать его ДО отправки в Telegram, а не после. Плюс rate-limit на границе (Vercel WAF/Firewall по IP с исключением для зального Wi-Fi) и понизить глобальный потолок ниже реального лимита Telegram на группу.

**H2. Тот же эндпоинт доверяет клиентским `table`/`sum` — можно отравить счёт ЛЮБОГО стола и подставить любую сумму**
`src/app/api/order/route.ts:33` *(объединяет находки 9+14)*
- Простыми словами: сервер не проверяет, что запрос реально пришёл со стола 12, и не берёт цену из меню — он складывает суммы, присланные клиентом. Можно прислать `{table:"12", label:"оскорбление", sum:1}` или `sum:999999`. Официант увидит это в «Счёте стола 12» и назовёт гостю сумму, выбранную атакующим. Заявленный «серверный пересчёт» — миф: сервер лишь пере-суммирует клиентские числа.
- Фикс: сменить контракт — клиент шлёт `id позиции + количество`, сервер берёт цену из авторитетного меню (`menu-cache`) и сам считает `sum`; клиентские суммы игнорировать. Подписанный токен стола в QR (HMAC(table_no, SECRET)), иначе `table=null`. Как минимум — проверка Origin/Referer. И честно переписать вводящий в заблуждение комментарий «клиенту не доверяем».

**H3. Тихий рассинхрон админка→сайт: при мигании БД на билде/ISR витрина «замерзает» на статическом `menu.ts` и теряет тег «menu» — правки из бота перестают доходить до сайта до передеплоя**
`src/lib/menu-cache.ts:50`, `src/app/menu/page.tsx:8` *(находка 6)*
- Простыми словами: если во время генерации страницы Neon мигнул (или `DATABASE_URL` не проброшен в билд-окружение), сайт молча отдаёт старые захардкоженные цены. Дальше владелец правит цену в боте, бот отвечает «✓ Сохранено», а сайт НЕ меняется — потому что застрявшая страница не помечена тегом, и сброс кэша её не трогает. Самый опасный класс бага: всё «выглядит сохранённым», но гость видит старое.
- Фикс: одна строка — `export const revalidate = 300;` в `src/app/menu/page.tsx` (навешивает TTL на кэш роута безусловно, даже если тегированный кэш упал). Проверить в `next build`, что `/menu` помечена как ISR, а не чистая static.

**H4. Всё меню спрятано за интро-оверлеем, который снимает только JS — при зависшем/упавшем JS гость за столом видит белый экран с логотипом**
`src/app/menu/menu-view.tsx:789`, `menu.css:42-117` *(находка 7)*
- Простыми словами: интро-заставку убирает только JavaScript. На нестабильном ресторанном Wi-Fi / старом браузере / с блокировщиком JS-чанк зависает — заставка не растворяется никогда, меню под ней не открыть. Ошибка не бросается, поэтому даже аварийный экран не срабатывает. Ядро продукта недоступно платящему гостю.
- Фикс: CSS-фейлсейф без JS — `@keyframes` с `animation-delay: 6s`, растворяющий `.mn-intro` (на рабочем пути React снимет раньше, анимация не доиграет). Доп. `<noscript>` для полностью отключённого JS.

### MEDIUM — тихая порча данных / потеря заказов при штатных сценариях

**M1. Надбавка к рецепту раков парсится как «все цифры подряд» → молчаливый 0 либо абсурдный overcharge**
`src/app/menu/menu-view.tsx:374`, `src/bot/raki-write-db.ts:103` *(находки 1+26)*
- Слова «плюс тысяча» → надбавка 0 ₽ (но гость её видит в чипе); «+1 000 ₽ (за 0,5 кг)» → склейка `1000+0+5` = **100 005 ₽**; «+1 тыс» → +1 ₽. Знак и дробь теряются всегда.
- Фикс: хранить сумму числом у источника (`recipe.extra`), а строку — только как ярлык; парсить в боте первую группу цифр и валидировать (пустая → ошибка «Укажите сумму»). Мёртвое поле `extra` (объявлено в 3 местах, нигде не читается) — как раз задействовать. Defense-in-depth на фронте: `match(/\d+/)` вместо конкатенации всех групп.

**M2. Напитки с вариантами (всё разливное/бутылочное пиво, чай, часть вод, квас, морс) молча не заказуемы через QR**
`src/app/menu/menu-view.tsx:18` *(находка 2)*
- Позиции показаны с ценой и форматами, но без кнопки «+ в заказ» и без модалки. В разделе «Пиво» заказуемы 2 из 7. Гость видит, но добавить не может — без объяснения. Потеря самообслуживания по маржинальной категории.
- Фикс: сделать строку с variants кликабельной (bottom-sheet с выбором формата → отдельная строка корзины на формат), либо быстро — по кнопке AddToCart на каждый формат. Спецлогику `orderable` оставить только для раков.

**M3. Whitelist огрызается «только для персонала» на КАЖДЫЙ реплай официанта в чате заказов**
`src/bot/bot.ts:408` *(находка 3)*
- Официант пишет «стол 5 готов» / реплай на тикет / `/help` → бот отвечает «доступен только персоналу» (хотя официант И ЕСТЬ персонал). Операционный чат зашумляется; риск, что бота замьютят и пропустят заказы.
- Фикс: вежливый отказ только в личке; в группах молчать (`ctx.chat?.type === "private"`). Барьер на меню-правки сохраняется.

**M4. Поле `table` (из URL `?t=`) нигде не валидируется по набору символов/длине → два симптома**
`src/app/api/order/route.ts:34`, `src/bot/bot.ts:124`, `src/lib/orders.ts:62` *(находки 4+16)*
- (а) Флуд уникальными именами столов раздувает `/столы` за 4096 символов Telegram → главный экран смены («открытые столы») не открывается весь 18-часовой хвост.
- (б) 20 эмодзи в `?t=` = 80 байт в `callback_data` > лимита 64 → заказ падает 502, тикет не создаётся (самоповреждение гостя).
- Фикс: жёсткий паттерн на `table_no` на границе API (`/^[0-9A-Za-zА-Яа-яЁё \-]{1,16}$/`), лимит вывода в `formatOpenTables` (≤60 строк + «…и ещё K столов»), долгосрочно — anti-abuse на публичный эндпоинт.

**M5. Оптимистичный лок не покрывает окно «отрисовали экран → применили ввод» для правок по индексу — параллельный админ молча правит НЕ ту позицию**
`src/bot/menu-write-db.ts:145`, `bot.ts:711/721` *(находка 5)*
- Жена жмёт 🗑 на «0,5л» (variant index 0); владелец в этот момент удалил вариант 0; свежее чтение сдвинуло индексы → удаляется «1л». Версия для лока читается в момент применения, а не рендера, поэтому «изменили параллельно» не срабатывает. Штатный сценарий двух заявленных админов.
- Фикс: ссылаться на variant/recipe по стабильному id (не по индексу массива), в callback передавать id; write ищет `findIndex` по id, не нашёл → чистая ошибка. Минимум — протаскивать render-time версию в state и сравнивать её при записи.

**M6. Пустая, но видимая глава рендерит «сломанную» секцию: заголовок + линия без содержимого + пустая пилюля в навигации**
`src/app/menu/menu-view.tsx:963` *(находка 8)*
- Крайне вероятно в day-1 новой бот-админки: владелец создаёт категорию (она сразу видима, без позиций) или ставит все позиции главы в стоп-лист — гость видит болтающийся раздел.
- Фикс: в `buildSections` отфильтровать пустые секции (`.filter(s => s.id === "raki" || s.entries.length > 0)`). Один источник питает и навигацию, и контент.

**M7. Новый напиток (вода/чай), добавленный через бота, попадает под подзаголовок «Пиво»**
`src/app/menu/menu-view.tsx:90` *(находка 11)*
- Фолбэк `group ?? "Пиво"` применяется ко ВСЕМ напиткам без группы, а бот `group_label` не задаёт. Добавили «Боржоми» в воды → гость видит его под «Пиво». Проявляется при каждом добавлении напитка через админку.
- Фикс: применять фолбэк «Пиво» только к разделу `beer`. Долгосрочно — дать боту задавать под-группу.

### LOW — баги и краевые случаи

- **L1.** Структурно-битый (но присутствующий) jsonb доски раков роняет `buildSections` и уводит ВСЁ меню в error boundary, минуя развязку раки↔главы. `menu-view.tsx:69` — валидировать форму доски после чтения в `menu-cache.ts`, битую → на статику раков *(нах. 22)*.
- **L2.** Переименование блюда в боте молча стирает его фото (фото берётся из хардкод-мапы `DISH_PHOTO[name]`, БД `photo`=NULL). `menu-view.tsx:1017` — перенести пути фото в сид-данные как поле `photo` по id *(нах. 23)*.
- **L3.** `claimUpdate` помечает апдейт обработанным ДО хендлера → таймаут/OOM лямбды (крупное фото + sharp) теряет апдейт навсегда, бот «молча замолкает». `bot.ts:344` — двухфазный claim (`done=false` до успеха, ретрай через 30с) *(нах. 29)*.
- **L4.** Guard-SELECT → UPDATE без `AND NOT is_deleted`: правка «успешно» применяется к позиции, параллельно ушедшей в soft-delete (TOCTOU во всех 5 скалярных сеттерах). `menu-write-db.ts:40` — объединить в один CTE-UPDATE с проверкой rowcount *(нах. 31)*.
- **L5.** `bot_state` ключуется только по `user_id` (не по чату): незавершённый диалог правки в личке + сообщение владельца в группе → правка молча съедает не тот объект. `bot.ts:818` — гейт `ctx.chat?.type !== "private"` в текст/фото-хендлерах *(нах. 18)*.
- **L6.** `addEntry` + `setState` не атомарны в мастере добавления: сбой `setState` после создания позиции → повтор создаёт дубль. `bot.ts:1067` — объединить в один CTE (INSERT+UPSERT state) *(нах. 17)*.
- **L7.** Неатомарный `MAX(sort_order)+1` → дубли порядка при двух админах; id категории `cat_<Date.now()>` → редкий PK-конфликт. `menu-write-db.ts:224` — тай-брейкер `ORDER BY sort_order, id` + добавить рандом-суффикс к id *(нах. 30)*.
- **L8.** Диалог не сбрасывается при «Позиция не найдена» → админ застревает в цикле ошибок до `/cancel`/TTL. `bot.ts:916` — в catch отличать «объект исчез» (сбросить) от «плохой ввод» через `getEntry` *(нах. 20)*.
- **L9.** `formatBill` без лимита длины → счёт заспамленного стола (>4096 символов) не открывается. `bot.ts:109` — кап ~3800 символов, ИТОГО добавлять всегда *(нах. 15)*.
- **L10.** Раки-фолбэк кешируется как `fallback:false` до 300с — деградация (статические цены раков вместо БД) невидима коду/владельцу. `menu-cache.ts:32` — отдельный флаг `rakiFallback` *(нах. 21)*.
- **L11.** `parseVariant` принимает научную/hex-нотацию без верхнего предела (`Number()`), в отличие от строгого `parsePrice` (`/^\d{1,7}$/`): «= 1e9» → 1 000 000 000 ₽. `menu-write-db.ts:189` — привести к тому же строгому паттерну *(нах. 19)*.
- **L12.** Цена «0,5 кг» у весовых — только для показа, развязана с начислением (`base×qty`): порцию 0,5 кг заказать нельзя (min 1 кг), а после правки базовой цены половинная цена на витрине расходится с фактом. `menu-view.tsx:1050` — выводить `price/2` вычислением от базы, не хранить отдельный variant *(нах. 13)*.

## 3. Халтура / техдолг (не баги, но срезано/недоделано)

- **«Серверный пересчёт» — переоценка.** Комментарии `route.ts:2,32` обещают «клиенту не доверяем, считаем на сервере», а по факту сервер лишь агрегирует клиентские суммы (см. H2). Как минимум — переписать комментарий честно: «валидируем формат и агрегируем; источник правды по деньгам — POS» *(нах. 14)*.
- **Дубль HTML-экранирования:** `escHtml` (`orders.ts:14`) и `esc` (`bot.ts:92`) — побайтово одинаковы в двух файлах, оба критичны для `parse_mode:HTML`. Правка безопасности в одном месте молча не попадёт во второе. Вынести единый `escapeHtml` в `src/lib/text.ts` *(нах. 24)*.
- **Мёртвый код:** `src/components/chapter-nav.tsx` (полноценный scroll-spy компонент) не импортируется нигде; та же логика переписана инлайном в `menu-view.tsx:817`. Плюс мёртвый CSS `.nav__*` в `globals.css`. Удалить *(нах. 25)*.
- **Мёртвое поле `extra`** в модели рецептов раков (объявлено в 3 местах, не читается) — вместо него хрупкий парсинг строки (см. M1) *(нах. 26)*.
- **Заголовки засеянных разделов захардкожены** в `LABEL`/`NAV_LABEL` (`menu-view.tsx:115`) и перекрывают БД — премиса «сайт читает из БД» нарушена для 14 базовых разделов. Плюс бот вообще не умеет переименовывать главы. Убрать хардкод, перенести кураторские названия в БД, добавить в бот операцию переименования главы *(нах. 27)*.
- **`RAKI_SECTION.entries` синтезируется на каждый рендер, но никогда не используется** (раки рендерятся через `<RakiBlock/>`). Заменить на `[] as MenuEntry[]` *(нах. 28)*.

## 4. ТОП-3 — что чинить первым

1. **Запереть публичный `/api/order`** (H1 + H2). Единственный удалённо-эксплуатируемый кластер: любой из интернета может (а) уронить приём заказов флудом/баном бота и (б) подставить произвольные позиции и суммы в счёт стола. До прода обязательно: атомарный лимит ДО отправки в Telegram + WAF-правило по IP + серверный источник цен + подписанный токен стола.
2. **Убить тихий рассинхрон админка→сайт** (H3). Одна строка `export const revalidate = 300` в `menu/page.tsx`. Дёшево, но закрывает самый коварный сценарий «бот сказал сохранено — сайт не изменился до передеплоя».
3. **CSS-фейлсейф для интро-оверлея** (H4). Один блок `@keyframes` — чтобы зависший на ресторанном Wi-Fi JS не оставлял гостя за столом с белым экраном вместо меню.

Все три — малый объём кода, максимальный эффект на реальную работу заведения.

## 5. Чего аудит НЕ покрыл / проверить руками

- **Всё — статический разбор, ноль рантайма.** Ни один сценарий не воспроизведён в браузере, реальном Telegram-боте или под нагрузкой. Флуд/DoS-находки (H1, M4, L9) — рассуждение, а не демонстрация. Прогнать реальный нагрузочный тест по staging-эндпоинту.
- **Telegram privacy-mode бота в группе** — внешняя настройка, не видна в коде, но от неё зависят находки M3 и L5 (насколько бот вообще видит свободный текст в группе). Проверить фактические настройки бота.
- **Vercel build-окружение:** проброшен ли `DATABASE_URL` в билд (корень H3). Проверить в настройках проекта.
- **Реальные лимиты Telegram на отправку в одну группу** vs потолок 80/мин — измерить, а не гадать.
- **Фото-пайплайн** (sharp OOM/timeout на Vercel, корень L3) — не измерялся. Протестировать реальным крупным фото с телефона: сохраняется ли, не теряется ли апдейт.
- **Состояние прод-БД vs `menu.ts`:** находки L2 (photo=NULL) и L12 (0,5кг совпадает с base/2) опираются на сид. Свериться с реальными данными.
- **Гонки двух админов** (M5, L4, L6, L7) — не воспроизведены вживую; проверить владелец+жена одновременно.
- **Изоляция транзакций Neon / поведение HTTP-драйвера под конкуренцией** — предположения в фиксах H1 проверить (advisory-lock vs SERIALIZABLE).
- **Продуктовое намерение по аутентификации `/api/order`** — задуман ли вообще QR-токен стола? Уточнить у владельца до выбора фикса H2.
- **Не смотрели:** покрытие тестами этих путей, доступность/реальные устройства для витрины меню, поведение при отключённом JS в реальных браузерах гостей, миграции схемы.
